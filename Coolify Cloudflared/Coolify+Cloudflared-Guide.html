Coolify behind a Cloudflare Tunnel

Set up coolify.yourdomain.com once, lock every inbound port on the VPS, and every app you deploy afterward inherits routing automatically — no repeat trips to the Cloudflare dashboard.

0inbound ports open
1wildcard route, forever
5tunnel routes total
~25 minclean VPS to live app

cloudflared always initiates the connection outward — Cloudflare never needs a way in.

This walkthrough covers three things in order:

  1. Standing up cloudflared on a clean VPS and pointing a tunnel at it.
  2. Installing Coolify and wiring its dashboard, realtime, and terminal traffic through that tunnel.
  3. Adding one wildcard route so every app you deploy afterward — today or a year from now — resolves without ever opening Cloudflare's dashboard again.

Prerequisites

Check these before starting — most setup problems trace back to one of them.

  • A domain on Cloudflare, with its nameservers already switched to Cloudflare's. Routes in step 2 auto-create DNS records, but only once Cloudflare is actually authoritative for the zone — if you just switched nameservers, give it time to propagate first.
  • A clean VPS (Debian or Ubuntu — the commands below are identical for both) with root or sudo SSH access.
  • No manual Docker install needed. Coolify's installer sets up Docker itself, so skip that step even if old guides mention it.
  • Sizing: 2 vCPU / 4 GB RAM is a comfortable floor for Coolify itself; add headroom if you'll build large images on the same box.
Placeholders used throughout

yourdomain.com, the tunnel name coolify-tunnel, and <YOUR_TUNNEL_TOKEN> are stand-ins. Swap in your real domain and the token from your own dashboard before running anything.

01

Create the tunnel

Done from the Cloudflare dashboard, then two commands run over SSH on the VPS.

1.1 — In the Cloudflare dashboard, pick your account, then go to Protect & Connect → Networking → Tunnels and click Create Tunnel.

1.2 — Name it something recognizable — coolify-tunnel works well — and confirm.

Treat the install token like a credential

Cloudflare's own dashboard flags this: the token generated in the next screen grants access to your account. Don't paste it into chat, commit it to a repo, or reuse one from a screenshot or tutorial — generate your own.

1.3 — Under Setup Environment, choose Debian as the operating system (it covers Ubuntu too) and 64-bit as the architecture. Two command blocks appear on that screen, each with its own copy icon and your real tunnel token already baked in.

Copy from Cloudflare's page, not from here

The two blocks below use <YOUR_TUNNEL_TOKEN> as a stand-in, so running them exactly as written will fail. They're shown only as a preview of what to expect — grab the real commands, token already included, from the matching screen in your own dashboard.

What to look for on Cloudflare's page

sudo cloudflared service install eyJhbGciOi***************NC…

↑ That highlighted icon is the one to click on your own dashboard — it copies the full command with your real token already in it.

Run both commands below in order over SSH on the VPS, using the real versions you just copied:

bash — install cloudflared Reference only 
# Add Cloudflare's package signing key
sudo mkdir -p --mode=0755 /usr/share/keyrings
curl -fsSL https://pkg.cloudflare.com/cloudflare-main.gpg | sudo tee /usr/share/keyrings/cloudflare-main.gpg >/dev/null

# Add the apt repository
echo 'deb [signed-by=/usr/share/keyrings/cloudflare-main.gpg] https://pkg.cloudflare.com/cloudflared any main' | sudo tee /etc/apt/sources.list.d/cloudflared.list

# Install
sudo apt-get update && sudo apt-get install cloudflared
bash — install as a service Reference only 
sudo cloudflared service install <YOUR_TUNNEL_TOKEN>

This installs cloudflared as a persistent systemd service — it survives reboots and reconnects on its own. The dashboard also shows a manual cloudflared tunnel run --token ... alternative; skip it unless you specifically want a foreground process instead of a service.

1.4 — Back in the dashboard, watch the Connection Status panel. It starts as "No connection detected yet" and flips to a green Connected state with your VPS hostname once the service is running. Don't move on until you see it.

If it stays disconnected

Check sudo systemctl status cloudflared on the VPS, then sudo journalctl -u cloudflared -f for the reason — almost always an outbound firewall blocking Cloudflare's edge IPs, or a stale token.

02

Wire up the routes

Open the tunnel you just created → Configure → Routes → Add route → Published Application.

Add these five, in this exact order — Cloudflare matches top to bottom, so specific rules must sit above the wildcard.

#SubdomainPathService URLPurpose
1 coolify /terminal/ws http://localhost:6002 In-browser terminal
2 coolify-realtime — http://localhost:6001 Realtime / websocket (Soketi)
3 coolify — http://localhost:8000 Coolify dashboard
4 @ (apex) — http://localhost:80 Bare yourdomain.com, if you ever deploy there
5 * — http://localhost:80 Catch-all → Coolify's Traefik proxy Do this once

Row 5 is the one that matters for never touching Cloudflare again: it hands routing off to Coolify's own Traefik proxy, which reads the Host header and forwards to whichever app you've assigned that domain to. myapp.yourdomain.com, blog.yourdomain.com — all of it resolves the moment you type the domain into Coolify and deploy.

Wildcards only cover one subdomain level

*.yourdomain.com covers app.yourdomain.com but not staging.app.yourdomain.com. For nested subdomains, add a specific route for that one, or use Cloudflare's Advanced Certificate Manager.

Cloudflare auto-creates the proxied CNAME records for each hostname. If a record already exists it won't be overwritten — if something doesn't resolve, check DNS → Records and point it manually at <tunnel-id>.cfargotunnel.com (proxied, orange cloud).

03

Install Coolify

One command, run as root or with sudo on the same VPS.

bash 
curl -fsSL https://cdn.coollabs.io/coolify/install.sh | sudo bash

The script installs Docker, creates Coolify's network, pulls its containers, and runs the first boot — a few minutes depending on the box. Leave the defaults alone: dashboard on 8000, proxy (Traefik) on 80/443, realtime (Soketi) on 6001, terminal websocket on 6002. The routes in step 2 are built around those exact ports.

04

Connect the realtime server

Point Coolify's Pusher/Soketi client at the tunnel instead of localhost.

SSH in and edit the env file:

bash 
nano /data/coolify/source/.env

Add these two lines — leave the existing APP_ID, PUSHER_APP_*, and REDIS_PASSWORD entries alone, they're already set from install:

.env 
PUSHER_HOST=coolify-realtime.yourdomain.com
PUSHER_PORT=443

Apply it by re-running the installer — it's idempotent and picks up the updated .env:

bash 
curl -fsSL https://cdn.coollabs.io/coolify/install.sh | sudo bash
05

Set your domains

In Coolify: Settings → General/Instance Settings, and the Domains field on every app you deploy.

  • Instance domain: http://coolify.yourdomain.com — http, not https.
  • Same rule for every future app: enter http://yourapp.yourdomain.com in Coolify's Domains field.
Why http, not https

Cloudflare terminates TLS at the edge — Coolify's Traefik only ever sees plain HTTP arriving over the tunnel. Set https:// on the Coolify side without a real cert installed on Traefik and you'll land in a TOO_MANY_REDIRECTS loop.

Need real end-to-end HTTPS later?

There's an advanced path using a Cloudflare Origin Certificate installed directly on Traefik — worth it if something like an OAuth callback needs genuine HTTPS all the way to the origin. It's a separate task from this setup, so tackle it only if you hit that need.

07

Lock down the firewall

This is the actual security win of using a tunnel — cloudflared only opens outbound connections.

Nothing needs to be open for inbound traffic at all. Close everything except SSH:

bash 
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow OpenSSH
sudo ufw enable
sudo ufw status verbose

You do not need to open 80, 443, 8000, 6001, or 6002 to the internet — cloudflared reaches them over localhost, and the default-deny policy blocks any direct hit on the VPS's public IP.

Using a custom SSH port?

Swap sudo ufw allow OpenSSH for sudo ufw allow <port>/tcp instead — and if you later sit behind a provider-level firewall (Hetzner Cloud Firewall, AWS security groups, etc.), mirror the same allow rules there.

08

Verify everything

Four checks, in order.

  • 1
    Dashboard loads. Visit https://coolify.yourdomain.com — it should load over HTTPS with no certificate warning.
  • 2
    Realtime works. Visit https://coolify.yourdomain.com/realtime and confirm a test event notification appears — that's the Soketi websocket connecting.
  • 3
    Terminal works. Open a deployed app's Terminal tab in Coolify and confirm it connects — that exercises port 6002.
  • 4
    Wildcard works. Deploy a throwaway app, set its domain to http://test.yourdomain.com, hit deploy, and confirm it's reachable — no Cloudflare changes required.

Deploying new apps

From here on, this is the entire routine.

Add the domain — http://whatever.yourdomain.com, or http://yourdomain.com for the apex — in the app's Domains field inside Coolify, and deploy. The wildcard tunnel route and Coolify's Traefik proxy handle the rest automatically. No new Cloudflare route, no new DNS record, no new certificate to think about.

Placeholders yourdomain.com, coolify-tunnel, and <YOUR_TUNNEL_TOKEN> throughout — swap in your real values before running any command.
